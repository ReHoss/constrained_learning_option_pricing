- When rapatriating results from Jean Zay (or any cluster) to local, **always offer the user the choice of including the optimiser checkpoints** before running the transfer. Checkpoint files (`checkpoint.pt` for L-BFGS variants, etc.) hold full optimiser state (curvature history, RNG, etc.) — typically 3–5 MB each, so several tens of MB across an ablation. They are only useful for resuming an interrupted run; if the user just wants to inspect figures / replot / diff metrics, excluding them via `rsync --exclude='checkpoint.pt'` cuts bandwidth and disk by ~3× (e.g. 44 MB → 11 MB for a 7-variant run). Three sensible options to offer: (1) "everything without checkpoints" (default, fastest); (2) "everything including checkpoints" (full, slow but enables resume); (3) "figures + summary only" (lightest, no replot possible). Use `rsync -avzP` so the transfer can resume on interruption.
- The `--debug` flag + smoke-test guard rule is defined globally in `~/.claude/CLAUDE.md`. Reference implementations in this repo: `experiments/python_scripts/exp_singularity_european_call/ablation_singularity_logS.py` (`SMOKE_TEST_NUM_ITERATIONS_THRESHOLD = 1000`) and `experiments/python_scripts/exp1/ablation_bermudan_formulation.py` (`SMOKE_TEST_ITERS_B_THRESHOLD = 200`) — copy the `debug_prefix` and threshold-guard pattern from either when adding a new ablation script.
- Long training loops should checkpoint periodically and support resume — capture everything needed for a faithful continuation (model, optimizer, scheduler, RNG, running metrics) so an interruption costs at most the checkpoint interval.
- Use explicit, propagated RNG handles rather than the implicit global state, and seed deterministically. The seed must be derived from an explicit, user-controlled field — never from cosmetic metadata such as the variant's display name, label, color, or iteration budget — so that two variants sharing the same hyperparameters produce the same initial weights and the same sampler trajectory. The default policy across an ablation is **shared seeding** (so that observed differences between variants reflect the method change, not RNG noise); decorrelated seeds are a deliberate opt-in for cases like ensembling, and even then the decorrelation key must be explicit. For variance estimates, add an explicit `seed` axis on top of the ablation.
- Concretely, every experiment script must expose a **master seed** as a CLI argument with a sensible default (e.g. `--seed 0`), and derive every per-role RNG (model init, sampler, evaluation, …) from that master via explicit role-tagged salts. The master seed is the single source of randomness for the whole run; per-role decorrelation is internal plumbing and must not depend on any other config field. Log the resolved master seed and every derived seed at startup so the log file remains a self-contained reproduction recipe.
- Track the best-loss state during training and restore it at the end — the last iter is not always the best one.
- Organise outputs into named subfolders rather than flat directories. Keep canonical artefacts separate from exploratory or diagnostic ones, and write each new diagnostic into its own subfolder so the canonical set stays clean. Avoid the opposite extreme of one-folder-per-file.
- The "SLURM logs in a dedicated `slurm/` subfolder" rule is defined globally in `~/.claude/CLAUDE.md`. In this repo it applies to every `sbatch` invocation under `bash_scripts/cluster/jeanzay/` and `bash_scripts/cluster/adastra/`.
- When orchestrating an ablation or sweep on a cluster, default to **sbatch job arrays** (one task per variant / seed / hyperparameter point) rather than a single sequential job. Variants are usually independent and the array gives a 4–10× wall-clock speedup at the same CPU/GPU-hour cost. For this to work the script must (i) accept a `--variant NAME` (or analogue) flag so each array task picks one entry, (ii) accept an output-directory override so all tasks write to a shared parent (otherwise per-task `datetime.now()` calls fragment the layout), and (iii) write per-task summary/state files (e.g. `summary_<name>.yaml`) rather than racing on a shared file. A follow-up `--replot` / finalize step then aggregates the per-task artefacts into the canonical comparison plots and combined `summary.yaml`.
- Cross-machine git topology: the laptop and the cluster may carry different remote sets — e.g. the laptop has only `origin → Overleaf`, the cluster has both `origin → GitHub` and `overleaf → Overleaf`. Overleaf HTTPS auth is unlikely to be configured non-interactively on the cluster, so propagating laptop commits via Overleaf will fail there. Workaround: register a `github` remote on the laptop pointing at the same repository the cluster's `origin` resolves to (`git@github.com:<user>/<repo>.git`), and `git push github master` after each batch of commits so the cluster can `git pull origin master` over its already-working SSH auth. Verify with `git log -1 --oneline github/master` after each push.
- Non-interactive SSH to Jean Zay strips the login profile, so `$WORK`, `idracct`, the module command, and any user shell function will be unset. Always wrap remote commands as `ssh jeanzay 'bash -lc "…"'` so a login shell sources `/etc/profile.d/` and `~/.bashrc`. Plain `ssh jeanzay 'cmd'` is fine only for direct binary invocations that don't depend on the IDRIS environment (e.g. `ssh jeanzay /usr/bin/hostname`).
- Cluster host-key trust on a fresh laptop: the first SSH attempt to Jean Zay's bastion + login node fails non-interactively with `Host key verification failed` until the user accepts the keys once. Have the user run `ssh jeanzay 'echo ok'` manually once and answer `yes` to both prompts (passerelle, then `jean-zay1.idris.fr`); after that, `BatchMode=yes` SSH from this session works.
- Shipping shell scripts to the cluster: nested SSH + `bash -lc "…"` + heredoc quoting is brittle and tends to break on `$VARIABLE` expansion and `"` escaping. Prefer writing the sbatch / setup script locally to `/tmp/<name>.sh`, then `scp` it to the cluster, then `ssh host 'sbatch /tmp/<name>.sh'`. Use SLURM filename pattern tokens (`%x-%j.out`, `%A_%a.out`) so the launcher doesn't need to know the job ID up front.
- Cluster venv bootstrap (Jean Zay): if the project venv exists on the cluster but is empty (only `pip` + `setuptools`), do the full install via `sbatch --partition=compil --account=<proj>@cpu --time=00:30:00 --wrap='source venv/.../activate && pip install --upgrade pip && pip install -e ".[ml]"'` rather than running pip on the login node. `compil` is non-billed, allows network egress to PyPI, and gives a clean compute environment for any wheels that need to build. Default pip resolution on Jean Zay pulls the **CUDA build** of torch (~2 GB of `nvidia-*` wheels even on a CPU-only project); pass `--index-url https://download.pytorch.org/whl/cpu` when a strict CPU-only build is needed. Either build runs on CPU with `--device cpu`, so the CUDA flavour is acceptable when disk is not a concern.
- SSH-driven workflow vs agent-to-agent handoff: when this session has working SSH to the cluster (key auth + host keys accepted), prefer driving the cluster directly from here — clone / pull, submit, poll `squeue`/`sacct`, rsync results back. ## Scientific methodology and writing register

Applies to every written output for this repository — reports, Markdown notes, docstrings, code comments, commit messages, figure titles and captions.

- Precise scientific and technical terminology; rigour is the priority and is not traded for brevity or a livelier tone. A longer phrasing is preferred when it is more exact.
- No colloquial, marketing, or sensational register ("for free", "buys", "huge win", "the story", "nice"). No spatial or physical-action metaphors for mathematical relations (a point *lies on* / *belongs to* / *converges to* a set, it does not "live in", "hug", or "sit"). No vague intensifiers — give the factor, count, or tolerance ("a factor of 6.0", not "much better"). No unexplained anthropomorphism of models or optimisers — state the optimisation or analytical fact.
- Passive or impersonal voice; no first person (we / our / I). "X is obtained by …", "Integrating … gives …".
- British English spelling and usage (normalise, behaviour, centre, parametrise, colour, neighbourhood). Established code and library identifiers keep their original spelling (e.g. `color=`, `normalize=`) — do not rename them.
- Distinguish and mark claim strength explicitly: proven / measured (with N) / conjectured / numerical artefact. `Proposition` / `Theorem` / `Lemma` with a `proof` environment are for **proven** statements only, and require an actual proof (even one line) or a first-sentence declaration of what is omitted. An empirical regularity — even one the field calls a "law" — is an **empirical finding**, never placed in a theorem environment and never given a `proof`. When a result has a provable part and a measured part, split them.
- Approximations use Landau notation with the limit written out ($f(x)=x+\tfrac{y}{2x}+o(y)$ as $y\to0$), never `\approx`. `\approx` is reserved for the decimal value of a numerical constant. Landau symbols appear only inside an `=` or `\le` with a named quantity on the left and an explicit limit.
- Claims about the state of practice or the literature ("widely used", "standard", "known in practice") require at least one citation, or must be reworded as a local observation.

## Mathematical notation (LaTeX in reports; LaTeX-in-Markdown for notes)

- Every symbol is introduced with its space of membership before use ($f:X\to Y$, $x\in\Omega$, regularity class where relevant). Do not use $f(x_0)$ before $f$ is typed.
- Definitions are carried by prose with a bare `=` ("let", "set", "define … by"); never `:=`, `\coloneqq`, or `\triangleq`. Do not chain a definition with a membership in one formula ("set $x=\ln s$, with $x\in\mathbb R$", not "$x=\ln s\in\mathbb R$").
- Derivatives use the operator, not a subscript ($\partial_x f$, not $f_x$). Give the evaluation point in the argument ($\partial_x f(0,R)$), never a restriction bar.
- Every recurring symbol is a **semantic LaTeX macro** defined once in the preamble; the body calls the macro. Reuse the bundled `notation.sty` — do not inline a glyph that duplicates or diverges from a macro it already defines. Macro and identifier names are long, multi-word, descriptive, acronym-free (`\boundaryDataExtension`, not `\ext`).

## Reproducibility (complements the logging / seed / checkpoint rules above)

- **Never report an inferred value as a measured one.** Every result number — table cell, figure, abstract, chat answer — must be read off a concrete run or saved artefact. If a value cannot be measured now (run not done, artefact missing), leave the slot **explicitly empty** (a dash, "not measured"), never a plausible-looking filler. A predicted value may accompany a measurement but never replace it, and must be typographically distinct.
- Provide a `--regenerate-figures` / `--replot` path that rebuilds every plot from saved artefacts (trained object + run-metadata + per-iteration history). Replotting reads saved tensors / metrics; it never recomputes them. A figure that can only be produced inside the training loop is a reproducibility defect.
- Catalogue generated datasets and major artefacts in an append-only registry (generating command, parameters, seed, output location) so a cited number traces back to the run that produced it. Exclude `_debug_` artefacts.

## Numerical clamps and truncations must not be silent

Any floor, ceiling, saturation, epsilon, positivity / realizability projection, gradient clip, or NaN / Inf guard that can change a value at runtime must report when it actually binds: WARNING on first activation, DEBUG afterwards, recording which clamp bound, how many elements it affected, and the most extreme raw (pre-clamp) value. A silently-active clamp regularises the very regime under study and can mask the phenomenon. Only a provably-inert epsilon (magnitude below any value the computation produces) may be left unlogged, with a comment stating why it is inert.

## Plot conventions

- Linestyle encodes the kind of curve: **solid** = trained / predicted / learned; **dashed** = analytical reference (closed form, finite-difference or binomial control, exact terminal condition, target); **dotted** = auxiliary annotation (raw payoff $(K-s)^+$, vertical markers, constants). Do not overload dashed / dotted for a trained variant.
- For a sweep whose axis is a hyperparameter, encode the axis in **colour** (sequential palette: viridis / plasma / magma); stroke stays solid.
- Place every legend **outside** the axes data area. Column headers, legend labels, and axis titles begin with a capital letter.

## Python style — match the surrounding code, no repo-wide reformatting

The existing code is consistent on the conventions that were actually followed (`snake_case`
naming throughout, a docstring on every module, Google-section docstrings on many functions).
Match the surrounding file's existing style when editing or adding code; do not impose a new
guide mid-development or reformat existing files (a wholesale switch — e.g. f-string to
pattern-string logging, symbol imports to module imports — is churn for no correctness gain).
Google-format docstrings (`Args:` / `Returns:` / `Raises:`) and explicit `X | None` types are
encouraged for new code because they already appear here, but they are not enforced retroactively.

## Prefer extending the tested infrastructure over throwaway scripts

When a task can be done either by a quick one-off script or by reusing / extending the existing library and experiment scripts (a library function, an existing script's CLI flag, the cluster launcher), prefer the latter. Promote reusable logic into `learning_option_pricing/` with tests rather than duplicating it in a script that will drift and go uncovered. A genuine scratchpad exploration that will not be kept belongs in a scratchpad directory, not the repository.
