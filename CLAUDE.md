# Project instructions

- The core of the package is in `learning_option_pricing/` while the python scripts used for experiments are under `experiments/`.
- The generated data from experiments **MUST** be stored in `data/<name_of_python_script>/<xp_folder>` where `<xp_folder>` is a timestamped folder containing the principal config values for the experiment. To enforce this mechanically (no hardcoded literal that can drift from the filename), every script derives its top-level data folder from `learning_option_pricing.utils.run_context.script_data_dir(__file__)`, which returns `<repo_root>/data/<Path(__file__).stem>/`. Callers append their own timestamped sub-folder, e.g. `out_dir = script_data_dir(__file__) / f"{timestamp}_{config_tag}"`. Never write a string literal like `Path("data/some_name")` in a script that produces experiment data — if you rename the script later, the data folder must follow automatically. For modules that intentionally stay torch-free (e.g. `exp_singularity_european_call/_ablation_catalogue.py`, used on Jean Zay login nodes), hard-code the runner-stem as a module-level constant (`RUNNER_SCRIPT_STEM = "..."`) and add a runtime assertion in the runner script (`assert _cat.RUNNER_SCRIPT_STEM == Path(__file__).stem`) so the two cannot drift.
- There is already some code under `experiments/` coming from a SciML project; this may be used as a reference for how to structure the experiments and store results.
- Please update `pyproject.toml` when needed and also the contribution guidelines in `CONTRIBUTING.md`.
- Document the implementation by updating the markdown files under `documents/methodology/`.
- In markdown files, please use LaTeX for mathematical expressions.
- Log as much information as possible in experiments and scripts. Concretely, every experiment log file must be self-contained: log at startup the full command line, Python version, PyTorch version, CUDA version and GPU name/memory; log every hyperparameter and variant config key; log the model parameter count and the RNG seeds used. Log a confirmation line each time a checkpoint is saved (with the full path and iteration number). At the end of training, log total wall-clock time, seconds-per-iteration, and the best loss value with the iteration at which it was achieved.
- the virtual environment is installed here venv/venv_learning_option_pricing
- Save the run statistics so that plots can be easily updated without re-running the experiments.
- Please also make sure the metrics are (reasonably) recorded per run so that figure patches can be applied without re-running the experiments
- Add a textbox below the figures that give the analytical formula for the symbols used in the figures.
- Labels figures when you think comparison are unfair.
- When running experiments, give the command to follow the progress of the experiment in real time. Please give the full absolute path to the log file so that it can be easily followed.
- be verbose, minimise acronyms, except for well-known ones. Be verbose in general with file and folder names, variable names, and comments in the code. This will make it easier for others to understand the code and contribute to the project.
- Code documentation must be in English.
- Favour muliple small commits with descriptive commit messages over large commits with vague messages.
- Before handing off work to a remote runner (Jean Zay agent, CI, or any cluster job), commit the relevant changes and push to the remote. The cluster only sees what is already in the upstream branch — local-only edits are invisible to it, so any change to scripts, configs, or `pyproject.toml` that the remote job will execute must land in a commit first.
- On Jean Zay (and IDRIS clusters in general), **never run computation on the login nodes**. Login nodes are for editing files, submitting jobs, and lightweight I/O only. Building a model, running a forward pass, calling autograd, or anything that allocates more than a few MB of tensors **must** go through a compute node — either an interactive shell (`srun --partition=prepost --time=00:05:00 --pty bash` for short CPU tasks; `--partition=gpu_p13 --gres=gpu:1` for GPU) or a batch job. The generic launcher in `bash_scripts/cluster/jeanzay/python/experiment_array_launcher.sh` is designed accordingly: its init phase on the login node only writes YAML/metadata files (no torch tensors), and every real Python invocation happens inside an sbatch task. When suggesting commands to be run on Jean Zay, default to `srun`/`sbatch` for anything that touches PyTorch beyond `import torch`.
- When rapatriating results from Jean Zay (or any cluster) to local, **always offer the user the choice of including the optimiser checkpoints** before running the transfer. Checkpoint files (`checkpoint.pt` for L-BFGS variants, etc.) hold full optimiser state (curvature history, RNG, etc.) — typically 3–5 MB each, so several tens of MB across an ablation. They are only useful for resuming an interrupted run; if the user just wants to inspect figures / replot / diff metrics, excluding them via `rsync --exclude='checkpoint.pt'` cuts bandwidth and disk by ~3× (e.g. 44 MB → 11 MB for a 7-variant run). Three sensible options to offer: (1) "everything without checkpoints" (default, fastest); (2) "everything including checkpoints" (full, slow but enables resume); (3) "figures + summary only" (lightest, no replot possible). Use `rsync -avzP` so the transfer can resume on interruption.
- **Every experiment script that produces a timestamped output folder MUST expose a `--debug` flag**, and every test / smoke run MUST use it (including the Jean Zay launcher). The flag prepends `_debug_` to the timestamped ablation directory so test runs are visually separated from real ones in `ls` (they cluster at the bottom because `_` sorts after digits in C/UTF-8 locale) and can be wiped en masse without touching real data. The cleanup one-liner is `find data -type d -name '_debug_*' -prune -exec rm -rf {} +` — safe to run any time. Never rely on remembering to delete a test directory by hand; if you start an experiment to verify code paths, hyperparameter ranges, or wall-clock estimates, that experiment must carry the `_debug_` prefix. Real ablations (the ones whose results you intend to keep, plot, cite, or rapatriate) MUST NOT use `--debug`. When adding a new ablation script, copy the `debug_prefix = "_debug_" if args.debug else ""` pattern used in `experiments/python_scripts/exp_singularity_european_call/ablation_singularity_logS.py` and `experiments/python_scripts/exp1/ablation_bermudan_formulation.py` — both the CLI flag and the prefix in the `script_data_dir(__file__) / f"{debug_prefix}{timestamp}_..."` construction. **Also copy the smoke-test guard**: each script defines a `SMOKE_TEST_..._THRESHOLD` constant (e.g. `SMOKE_TEST_ITERS_B_THRESHOLD = 200` in `ablation_bermudan_formulation.py`, `SMOKE_TEST_NUM_ITERATIONS_THRESHOLD = 1000` in `ablation_singularity_logS.py`) set to ~3–10% of the real-run iteration budget, and aborts via `parser.error` / `SystemExit` if the user passes an iter count below the threshold without `--debug`. This makes it mechanically impossible to produce an unflagged smoke-test output folder — the rule was previously enforced only by convention and slipped on 2026-05-12 (folder `20260512_220622_analyticalA_itersB30`, since renamed to `_debug_…`). The guard sits right after argparse + YAML translation and is bypassed only for `--replot` (no training in that mode). If you ever need a deliberately short real run, raise the iter count above the threshold; otherwise pass `--debug` to flag it as exploratory.
- Long training loops should checkpoint periodically and support resume — capture everything needed for a faithful continuation (model, optimizer, scheduler, RNG, running metrics) so an interruption costs at most the checkpoint interval.
- Use explicit, propagated RNG handles rather than the implicit global state, and seed deterministically. The seed must be derived from an explicit, user-controlled field — never from cosmetic metadata such as the variant's display name, label, color, or iteration budget — so that two variants sharing the same hyperparameters produce the same initial weights and the same sampler trajectory. The default policy across an ablation is **shared seeding** (so that observed differences between variants reflect the method change, not RNG noise); decorrelated seeds are a deliberate opt-in for cases like ensembling, and even then the decorrelation key must be explicit. For variance estimates, add an explicit `seed` axis on top of the ablation.
- Concretely, every experiment script must expose a **master seed** as a CLI argument with a sensible default (e.g. `--seed 0`), and derive every per-role RNG (model init, sampler, evaluation, …) from that master via explicit role-tagged salts. The master seed is the single source of randomness for the whole run; per-role decorrelation is internal plumbing and must not depend on any other config field. Log the resolved master seed and every derived seed at startup so the log file remains a self-contained reproduction recipe.
- Track the best-loss state during training and restore it at the end — the last iter is not always the best one.
- Organise outputs into named subfolders rather than flat directories. Keep canonical artefacts separate from exploratory or diagnostic ones, and write each new diagnostic into its own subfolder so the canonical set stays clean. Avoid the opposite extreme of one-folder-per-file.
- **Every `slurm-*.out` / `slurm-*.err` file produced by a SLURM job MUST land in a dedicated `slurm/` subfolder of the ablation directory**, never at the top level alongside `metadata.yaml`, `comparison/`, the per-variant subdirs, etc. The slurm logs are operational noise (driver output, sbatch boilerplate, queue diagnostics) — keeping them out of the top level means `ls <expdir>` shows only canonical artefacts. Concretely, every `sbatch` invocation in `bash_scripts/cluster/jeanzay/` must build `SLURM_LOG_DIR="$EXPDIR/slurm"`, `mkdir -p` it, and pass `--output="$SLURM_LOG_DIR/slurm-...%j..."  --error="$SLURM_LOG_DIR/slurm-...%j..."`. When inheriting an older run directory whose slurm files are at the top level, move them: `mkdir -p <expdir>/slurm && find <expdir> -maxdepth 1 -type f -name 'slurm-*' -exec mv {} <expdir>/slurm/ \;`.
- When orchestrating an ablation or sweep on a cluster, default to **sbatch job arrays** (one task per variant / seed / hyperparameter point) rather than a single sequential job. Variants are usually independent and the array gives a 4–10× wall-clock speedup at the same CPU/GPU-hour cost. For this to work the script must (i) accept a `--variant NAME` (or analogue) flag so each array task picks one entry, (ii) accept an output-directory override so all tasks write to a shared parent (otherwise per-task `datetime.now()` calls fragment the layout), and (iii) write per-task summary/state files (e.g. `summary_<name>.yaml`) rather than racing on a shared file. A follow-up `--replot` / finalize step then aggregates the per-task artefacts into the canonical comparison plots and combined `summary.yaml`.
